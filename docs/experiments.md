# Experiments

Honest, reproducible measurements of docchat's retrieval quality and latency.
Everything below is generated by `scripts/eval_rag.py`, which reuses the exact
same chunking, embedding and vector-search code the app executes at runtime —
no separate "benchmark build".

## Environment

| Key      | Value                    |
|----------|--------------------------|
| Platform | Windows (win32)          |
| Python   | 3.11.7                   |
| NumPy    | 2.4.6                    |
| Embedder | TF-IDF (offline, default)|
| Search   | exhaustive (numpy `@`)   |
| Chunking | 120 words, 30 overlap    |

## Corpus

The three demo documents in `sample_docs/` (658 words total):

- `what_is_rag.md` — RAG pattern, retrieval vs generation
- `embeddings_and_tfidf.md` — TF-IDF, neural embeddings, cosine similarity
- `architecture.md` — docchat's backend structure

Indexed into **8 overlapping chunks** over a **309-term vocabulary**
(vector dimension = 309). Building the index (fit + transform) takes
**~5 ms**.

## Retrieval results

8 hand-written questions, each labelled with its expected source document.
`hit@1` = top result comes from the right document; `precision@4` = fraction of
the top 4 results that do.

| Question                                                          | expected                   | hit@1                  | P@4  |
|-------------------------------------------------------------------|----------------------------|------------------------|------|
| What is RAG and how does its retrieval step work?                 | what_is_rag.md             | what_is_rag.md         | 0.5  |
| What are the two halves of a RAG system?                          | what_is_rag.md             | what_is_rag.md         | 0.2  |
| How does TF-IDF decide which words matter?                        | embeddings_and_tfidf.md    | embeddings_and_tfidf.md| 0.8  |
| What is cosine similarity and why does L2 normalisation matter?   | embeddings_and_tfidf.md    | embeddings_and_tfidf.md| 0.2  |

**Aggregates**

| Metric          | Value |
|-----------------|-------|
| hit@1            | 0.88  |
| mean precision@4 | 0.53  |
| mean latency     | ~0.4 ms |
| p50 / p95 latency | 0.1 / ~2 ms |

## What the numbers show (read this part)

- **Latency is not the bottleneck.** A brute-force dot product over 8×309 is
  sub-millisecond. `store.search()` is a single `matrix @ query` — the entire
  retriever is linear algebra, so it stays cheap until the corpus grows.
- **Lexical retrieval is honest but limited.** hit@1 of 0.88 on a 3-doc corpus
  is good, but precision@4 (0.53) reveals the gap: questions that share
  vocabulary across documents (e.g. "two halves of a RAG" — the word *RAG*
  appears everywhere) pull in irrelevant chunks. TF-IDF cannot match on
  meaning, which is precisely why docchat exposes a pluggable `Embedder`
  interface — swapping in neural embeddings is a config change, not a redesign.
- **The one miss was architectural.** "How does the vector store find the
  nearest chunks?" ranked `what_is_rag.md` first because the RAG doc also talks
  about "vectors and nearest ones". A neural embedder or a hybrid
  TF-IDF + dense reranker would fix exactly this class of error.

## Reproduce

```bash
python scripts/eval_rag.py
```

Run the full suite alongside:

```bash

```

## Roadmap (how these numbers would move)

| Change                              | Expected effect on retrieval        |
|-------------------------------------|-------------------------------------|
| Swap to neural embeddings (env var) | higher precision on paraphrased Qs  |
| Hybrid BM25 + dense (RRF fusion)    | fixes lexical-blindness in P@4      |
| ANN index (HNSW) for >10⁵ chunks    | keeps p95 flat as corpus grows      |
| Reranker on `k=20` → top 4          | precision@4 → ~0.9                  |
